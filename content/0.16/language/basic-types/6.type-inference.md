## Inference without magic

Zig infers types so you can skip redundant annotations — but it never guesses in a way that hides allocation, control flow, or overflow. Inference is **local and predictable**: the compiler looks at the value you wrote and the place you used it.

---

## Inferring `const` bindings

For `const`, Zig often has everything it needs from the initializer:

```zig test
const std = @import("std");

test "const inference" {
    const answer = 42; // comptime_int
    const pi = 3.14; // comptime_float
    const ok = true; // bool
    const hi = "hello"; // *const [5:0]u8

    // Use them in typed contexts — they coerce:
    const as_u32: u32 = answer;
    try std.testing.expectEqual(@as(u32, 42), as_u32);
    try std.testing.expect(ok);
    try std.testing.expectEqualStrings("hello", hi);
    _ = pi;
}
```

| Initializer | Inferred type |
| --- | --- |
| `42`, `0xff`, `1_000` | `comptime_int` |
| `3.14`, `1e-3` | `comptime_float` |
| `true` / `false` | `bool` |
| `"text"` | `*const [N:0]u8` |
| `.{ 1, true }` | Struct tuple (anonymous) |
| `[_]i32{1, 2}` | `[2]i32` |

## Why `var` is stricter

A runtime `var` needs a **concrete** type that exists at runtime. `comptime_int` is not one of those:

```zig
// var x = 42;
// error: unable to infer variable type / comptime_int not allowed here
```

Give it a type or coerce the literal:

```zig test
const std = @import("std");

test "var needs a concrete type" {
    var x: u32 = 42;
    var y = @as(i32, -7);
    x += 1;
    y += 1;
    try std.testing.expectEqual(@as(u32, 43), x);
    try std.testing.expectEqual(@as(i32, -6), y);
}
```

::callout{type="tip"}
Rule of thumb: `const` + literal → often untyped comptime number; `var` → always name a runtime type (annotation or `@as`).
::

## Inspecting types with `@TypeOf`

`@TypeOf` is a compile-time builtin that returns the type of an expression as a `type` value:

```zig test
const std = @import("std");

test "@TypeOf" {
    const T = @TypeOf(42);
    try std.testing.expect(T == comptime_int);

    const s: []const u8 = "zig";
    try std.testing.expect(@TypeOf(s) == []const u8);
}
```

This is invaluable in generic code and when debugging “what type did I actually get?”

## Contextual typing

Zig also pushes types **inward** from the surrounding context:

```zig test
const std = @import("std");

test "context narrows literals" {
    const x: u64 = 42; // literal becomes u64 here
    const y = x + 10; // y is u64 — peer with x
    try std.testing.expectEqual(@as(u64, 52), y);
}
```

Function parameters and return types do the same:

```zig test
const std = @import("std");

fn double(n: u32) u32 {
    return n * 2; // 2 coerces to u32
}

test "parameter context" {
    try std.testing.expectEqual(@as(u32, 10), double(5));
}
```

## Peer type resolution (again)

When branches produce values, peers must agree:

```zig test
const std = @import("std");

test "peers in if expression" {
    const flag = true;
    const msg = if (flag) "yes" else "no"; // both *const [N:0]u8 → coerce to common
    try std.testing.expectEqualStrings("yes", msg);
}
```

If peers conflict, annotate:

```zig test
const std = @import("std");

test "fix peer conflict" {
    const flag = false;
    // Without help, u32 vs i32 refuse to meet:
    // const bad = if (flag) @as(u32, 1) else @as(i32, -1);

    const good: i64 = if (flag) 1 else -1;
    try std.testing.expectEqual(@as(i64, -1), good);
}
```

## Result location awareness

Zig is **result-type aware**: the type of the place you are initializing can flow into the expression. That is why this works without annotating the struct literal's type in many cases (when the destination is known), and why `return 0` knows which integer type the function wants.

```zig test
const std = @import("std");

const Point = struct { x: i32, y: i32 };

fn origin() Point {
    return .{ .x = 0, .y = 0 }; // result type is Point
}

test "result type" {
    const p = origin();
    try std.testing.expectEqual(@as(i32, 0), p.x);
}
```

## `comptime` and generic inference

Marking a scope or parameter `comptime` forces evaluation at compile time and unlocks type-level programming:

```zig test
const std = @import("std");

fn Matrix(comptime T: type, comptime rows: usize, comptime cols: usize) type {
    return [rows][cols]T;
}

test "comptime type function" {
    const Mat2x2 = Matrix(f32, 2, 2);
    const m: Mat2x2 = .{
        .{ 1, 0 },
        .{ 0, 1 },
    };
    try std.testing.expectEqual(@as(f32, 1), m[0][0]);
}
```

Here Zig infers nothing mystical — you **passed** `T`, `rows`, and `cols` as compile-time values, and the function **returned** a type. That pattern (`fn (…) type`) is how much of the standard library implements generics.

Parameters can mix runtime and comptime:

```zig test
const std = @import("std");

fn first(comptime T: type, items: []const T) T {
    return items[0];
}

test "generic function" {
    const nums = [_]i32{ 9, 8, 7 };
    try std.testing.expectEqual(@as(i32, 9), first(i32, &nums));
}
```

Often you can even omit the explicit `T` when it is inferable from arguments — depending on the function signature and call site. When inference fails, pass `T` explicitly.

## Annotated vs inferred: when to write types

| Prefer annotation | Prefer inference |
| --- | --- |
| Public function signatures | Local `const` with obvious initializer |
| `var` bindings | Intermediate `const` values |
| API boundaries | `@as` only when needed for peers/literals |
| Complex structs you want documented | Short-lived temporaries |

::callout{type="info"}
Clarity beats cleverness. If a reader must run a mental type-checker for three lines, add an annotation.
::

## Common inference errors (and fixes)

**“Unable to infer type” on `var`**  
→ Add `: T` or `@as(T, …)`.

**“Peer type resolution failed”**  
→ Make branches share a type with `@as` or a parent annotation.

**“Comptime-only type used at runtime”**  
→ Coerce `comptime_int` / `comptime_float` into a runtime numeric type before storing in `var` or passing where a runtime value is required.

**“Expected type X, found Y”**  
→ Use the conversion builtins from the previous page (`@intCast`, `@floatFromInt`, …) when coercion is not enough.

---

## Mini checklist

1. Literals stay comptime-typed until a runtime type claims them.
2. `const` infers freely; `var` needs a runtime type.
3. Context and result locations push types into expressions.
4. Peers must agree — help them with `@as` or annotations.
5. `comptime` parameters turn types and numbers into generic building blocks.

You now have a solid grip on values and types. Next up: **control flow** — `if`, loops, `switch`, and labeled blocks — where these types meet decisions and repetition.
