## Declaring values

Value assignment in Zig uses a simple, explicit form:

<div class="syntax-form">
  <code><span class="sf-kw">const</span><span class="sf-op">|</span><span class="sf-kw">var</span> <span class="sf-id">identifier</span><span class="sf-opt">[: type]</span> <span class="sf-op">=</span> <span class="sf-val">value</span></code>
</div>

| Piece | Meaning |
| --- | --- |
| `const` | Immutable binding — the name always refers to the same value |
| `var` | Mutable binding — you may reassign or mutate it later |
| `: type` | Optional type annotation; Zig can often infer the type |
| `= value` | **Required** — every binding needs an initial value |

```zig test
const std = @import("std");

test "const and var" {
    const answer: i32 = 42; // immutable signed 32-bit integer
    var counter: u32 = 0; // mutable unsigned 32-bit integer
    counter += 1;

    try std.testing.expectEqual(@as(i32, 42), answer);
    try std.testing.expectEqual(@as(u32, 1), counter);
}
```

::callout{type="tip"}
Prefer `const` whenever you can. Immutability makes intent clearer and helps the compiler catch mistakes. Reach for `var` only when the value must change.
::

## Type annotations and inference

You can write the type next to the name, or let Zig infer it from the right-hand side:

```zig test
const std = @import("std");

test "type annotations and inference" {
    // Explicit type
    const explicit: i32 = 5;

    // Inferred via @as — useful when you want a concrete runtime type
    const inferred = @as(i32, 5);
    var count = @as(u32, 5000);

    try std.testing.expectEqual(explicit, inferred);
    try std.testing.expectEqual(@as(u32, 5000), count);
}
```

`@as(T, value)` is an explicit, *safe* coercion. It only works when Zig can convert `value` to `T` without losing information in a way the language forbids. You will use it often when a bare literal would otherwise stay a compile-time-only type.

Bare integer and float literals are special:

```zig test
const std = @import("std");

test "literal types" {
    const n = 42; // comptime_int — arbitrary precision at compile time
    const pi = 3.14; // comptime_float

    // They coerce into concrete types when used in a typed context:
    const as_i32: i32 = n;
    const as_f64: f64 = pi;

    try std.testing.expectEqual(@as(i32, 42), as_i32);
    try std.testing.expect(as_f64 > 3.0);
}
```

::callout{type="warning"}
A bare `var x = 42;` is a **compile error**. Integer literals are `comptime_int`, which cannot live in a runtime mutable slot. Give `var` a type annotation or use `@as`:

```zig
var x: i32 = 42;
// or
var y = @as(i32, 42);
```
::

## Everything needs a value

Unlike some languages, Zig does not allow empty declarations. If you truly do not have a meaningful value yet, you must still initialize — either with a real default, or with `undefined` **and** a type annotation:

```zig test
const std = @import("std");

test "undefined initialization" {
    var buffer: [4]u8 = undefined;
    buffer = .{ 1, 2, 3, 4 };
    try std.testing.expectEqual(@as(u8, 1), buffer[0]);
}
```

```zig
const a: i32 = undefined;
var b: u32 = undefined;
```

### What `undefined` really means

If you are coming from JavaScript, **do not** treat Zig's `undefined` like JS `undefined`.

| Language | Meaning of “undefined” |
| --- | --- |
| JavaScript | A real value you can test for (`x === undefined`) |
| Zig | “I claim this memory is uninitialized” — reading it is **illegal behaviour** |

Zig's `undefined` is closer to C's uninitialized stack variable or Rust's `MaybeUninit` without the safety rails. Safety builds may poison the memory so misuse is easier to catch; ReleaseFast may not. Never use `undefined` as a stand-in for “no value.”

::callout{type="info"}
When a value may be absent, use an **optional** (`?T`) and `null` instead. Optionals are covered later; they are the safe, intentional way to model missing data.
::

## Reassignment and mutation

Only `var` bindings can be reassigned:

```zig test
const std = @import("std");

test "reassignment" {
    var score: i32 = 10;
    score = 20; // OK
    score += 5; // OK — compound assignment
    try std.testing.expectEqual(@as(i32, 25), score);

    // const locked: i32 = 1;
    // locked = 2; // compile error: cannot assign to constant
}
```

Zig supports the usual compound operators: `+=`, `-=`, `*=`, `/=`, `%=`, and the bitwise forms `&=`, `|=`, `^=`, `<<=`, `>>=`.

## No shadowing

Zig does **not** allow shadowing: you cannot redeclare a name that is already in scope, even inside a nested block. That prevents a whole class of “I thought I was updating `x`” bugs. Pick a new name, or reassign a `var` instead of redeclaring.

## Quick reference

```zig
const name: Type = value;   // immutable, typed
var name: Type = value;     // mutable, typed
const name = @as(Type, v);  // immutable, type via @as
var name: Type = undefined; // mutable, deliberately uninitialized
```

### Good habits

1. Default to `const`.
2. Annotate types on public APIs and when inference is unclear.
3. Use `@as` when you need a concrete type from a literal.
4. Avoid `undefined` unless you will write every byte before any read.
5. Prefer optionals (`?T`) over sentinel “empty” values when absence is meaningful.
