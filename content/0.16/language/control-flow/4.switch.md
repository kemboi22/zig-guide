## Multi-way branch with `switch`

`switch` chooses a prong based on a value. In Zig it is an **expression**: every prong must produce a compatible result type (or diverge with `return` / `unreachable` / etc.).

```zig test
const std = @import("std");

test "basic switch" {
    const x: u32 = 2;

    const result = switch (x) {
        0 => "zero",
        1 => "one",
        2 => "two",
        else => "many",
    };

    try std.testing.expectEqualStrings("two", result);
}
```

There is no implicit fall-through between prongs (unlike C). Each match is independent.

## Exhaustiveness

Zig requires that **every possible value** is handled. That is a major safety feature:

- For small integers and enums, cover all cases or use `else`.
- For large types like `u32`, you almost always need `else` (or ranges that cover the space).

```zig test
const std = @import("std");

test "switch exhaustiveness with ranges" {
    const x: u8 = 100;

    const result = switch (x) {
        0...9 => "small",
        10...99 => "medium",
        else => "large",
    };

    try std.testing.expectEqualStrings("large", result);
}
```

### Enums without `else`

When every enum variant is listed, omit `else`. If you add a variant later, the compiler forces you to update the switch:

```zig test
const std = @import("std");

const Color = enum { red, green, blue };

test "switch on enum" {
    const c = Color.green;

    const hex = switch (c) {
        .red => "#FF0000",
        .green => "#00FF00",
        .blue => "#0000FF",
    };

    try std.testing.expectEqualStrings("#00FF00", hex);
}
```

::callout{type="tip"}
Exhaustive enum switches are one of Zig's best refactoring tools. Adding a variant becomes a compile error everywhere you forgot to handle it — by design.
::

## Ranges

Inclusive ranges use `...` inside switch prongs:

```zig test
const std = @import("std");

test "switch grade ranges" {
    const score: u32 = 85;

    const grade = switch (score) {
        0...49 => "F",
        50...69 => "D",
        70...79 => "C",
        80...89 => "B",
        90...100 => "A",
        else => "invalid",
    };

    try std.testing.expectEqualStrings("B", grade);
}
```

::callout{type="info"}
In `switch`, `0...9` is an **inclusive** range (both ends included). That differs from the half-open `0..10` used in `for` loops. Remember: switch ranges use three dots.
::

## Multiple items per prong

Comma-separate values that share a body:

```zig test
const std = @import("std");

test "switch multiple items" {
    const c: u8 = 'a';

    const is_vowel = switch (c) {
        'a', 'e', 'i', 'o', 'u' => true,
        else => false,
    };

    try std.testing.expect(is_vowel);
}
```

## Blocks in prongs

When a prong needs multiple statements, use a block. The block's value is what the prong yields (via the last expression pattern with `break` from a labeled block, or simply use statements when `switch` is not producing a value):

```zig test
const std = @import("std");

test "switch prong with block" {
    const x: u32 = 1;

    const description = switch (x) {
        0 => "none",
        1 => blk: {
            const detail = "exactly one";
            break :blk detail;
        },
        else => "several",
    };

    try std.testing.expectEqualStrings("exactly one", description);
}
```

## Tagged unions

`switch` is the natural way to unpack a tagged union. Capture the payload with `|name|`:

```zig test
const std = @import("std");

const Value = union(enum) {
    int: i64,
    float: f64,
    text: []const u8,
};

test "switch tagged union" {
    const v = Value{ .float = 3.14 };

    const desc = switch (v) {
        .int => |i| blk: {
            _ = i;
            break :blk "integer";
        },
        .float => |f| blk: {
            try std.testing.expect(f > 3.0);
            break :blk "float";
        },
        .text => |s| blk: {
            _ = s;
            break :blk "string";
        },
    };

    try std.testing.expectEqualStrings("float", desc);
}
```

Pointer captures work here too: `|*payload|` when you need to mutate the active field.

## `switch` as a statement

When you only need side effects, discard the result:

```zig test
const std = @import("std");

test "switch as statement" {
    const x: u32 = 1;
    var saw: []const u8 = "none";

    switch (x) {
        0 => saw = "zero",
        1 => saw = "one",
        else => saw = "other",
    }

    try std.testing.expectEqualStrings("one", saw);
}
```

## Switching on booleans and more

Any type that supports equality comparison in the ways Zig allows can appear in a switch subject — integers, enums, error sets, and more. Booleans work but are usually clearer as `if`.

```zig test
const std = @import("std");

test "switch on error" {
    const err: anyerror = error.NotFound;

    const msg = switch (err) {
        error.NotFound => "missing",
        error.OutOfMemory => "oom",
        else => "other",
    };

    try std.testing.expectEqualStrings("missing", msg);
}
```

## `else` vs `unreachable`

| Prong | Use when |
| --- | --- |
| `else => …` | Remaining cases are possible and handled |
| `else => unreachable` | Remaining cases must be impossible — bug if hit |

```zig test
const std = @import("std");

test "else unreachable" {
    const bit: u1 = 1;

    const label = switch (bit) {
        0 => "off",
        1 => "on",
        // u1 has only 0 and 1 — no else needed
    };

    try std.testing.expectEqualStrings("on", label);
}
```

## Common mistakes

1. **Missing exhaustiveness** — handle all cases or add `else`.
2. **Using `..` instead of `...` in switch ranges.**
3. **Expecting C-style fall-through** — it does not exist; list multiple items in one prong instead.
4. **Forgetting captures on unions** — `.tag => |payload|` is how you access the field.

```zig
const r = switch (value) {

    else => "other",

    .a => |payload| { … },
    .b => |*ptr| { ptr.* = …; },
}
```
