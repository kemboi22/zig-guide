## Iterate collections with `for`

When you have an array, slice, or range, `for` is the clear tool. Each iteration **captures** the current element:

```zig test
const std = @import("std");

test "basic for" {
    const items = [_]u32{ 1, 2, 3, 4 };
    var sum: u32 = 0;

    for (items) |val| {
        sum += val;
    }

    try std.testing.expectEqual(@as(u32, 10), sum);
}
```

The `|val|` capture is a **copy** of each element by default (for simple types). The loop variable is immutable unless you capture a pointer (below).

## Ranges

Zig ranges pair naturally with `for`. The form `start..end` is a half-open range: it includes `start` and excludes `end`.

```zig test
const std = @import("std");

test "for over range" {
    var sum: u32 = 0;
    for (0..5) |i| {
        sum += @intCast(i);
    }
    // 0+1+2+3+4
    try std.testing.expectEqual(@as(u32, 10), sum);
}
```

## Index capture

Need the index as well as the value? Zip the collection with a range:

```zig test
const std = @import("std");

test "for with index" {
    const items = [_]u32{ 10, 20, 30 };

    for (items, 0..) |val, idx| {
        try std.testing.expectEqual(val, items[idx]);
    }
}
```

`0..` means “from 0 upward” and is length-matched to the other sequence. You can also write an explicit end:

```zig
for (items, 0..items.len) |val, idx| {
    _ = val;
    _ = idx;
}
```

::callout{type="tip"}
`for (items, 0..) |val, idx|` is the idiomatic “enumerate” pattern — Zig has no separate `enumerate` keyword.
::

## Pointer capture — mutate elements

To modify elements in place, iterate pointers:

```zig test
const std = @import("std");

test "for pointer capture" {
    var items = [_]u32{ 1, 2, 3 };

    for (&items) |*ptr| {
        ptr.* *= 2;
    }

    try std.testing.expectEqual(@as(u32, 2), items[0]);
    try std.testing.expectEqual(@as(u32, 4), items[1]);
    try std.testing.expectEqual(@as(u32, 6), items[2]);
}
```

| Capture | Meaning |
| --- | --- |
| `|x|` | Immutable copy / view of element |
| `|*x|` | Pointer to element — mutate with `x.*` |

For slices of larger structs, pointer capture also avoids copying heavy values when you only need to read through a pointer — though `|x|` on a slice of structs often already gives you a const reference-like binding depending on context; when you need mutation, `|*x|` is the explicit tool.

## Multiple sequences

`for` can walk several sequences **in lockstep**. They must be the same length:

```zig test
const std = @import("std");

test "for multiple sequences" {
    const a = [_]u32{ 1, 2, 3 };
    const b = [_]u32{ 10, 20, 30 };
    var sum: u32 = 0;

    for (a, b) |va, vb| {
        sum += va + vb;
    }

    // (1+10)+(2+20)+(3+30) = 66
    try std.testing.expectEqual(@as(u32, 66), sum);
}
```

A length mismatch is a safety-checked illegal behaviour (runtime panic in safe modes) or a compile error when lengths are comptime-known and disagree.

## `for` as an expression

Like `while`, `for` can produce a value. `break value` yields from the loop; `else` runs if the loop finishes without breaking:

```zig test
const std = @import("std");

test "for as expression" {
    const items = [_]u32{ 1, 2, 3, 4, 5 };

    const found = for (items) |val| {
        if (val == 3) break true;
    } else false;

    try std.testing.expect(found);
}
```

```zig test
const std = @import("std");

test "for search with payload" {
    const items = [_]u32{ 10, 20, 30, 40 };

    const first_big: u32 = for (items) |val| {
        if (val > 25) break val;
    } else 0;

    try std.testing.expectEqual(@as(u32, 30), first_big);
}
```

## Nested loops and labels

You can nest `for` loops freely. Labels (covered fully in Blocks & Labels) let you `break` or `continue` an outer loop:

```zig test
const std = @import("std");

test "nested for with label" {
    var found = false;

    outer: for (0..4) |i| {
        for (0..4) |j| {
            if (i == 2 and j == 3) {
                found = true;
                break :outer;
            }
        }
    }

    try std.testing.expect(found);
}
```

## Inline for

`inline for` unrolls at compile time. It is perfect for tuples, type lists, and small fixed sets where each iteration may involve different types:

```zig test
const std = @import("std");

test "inline for" {
    const fields = .{ "a", "b", "c" };
    comptime var result: []const u8 = "";

    inline for (fields) |field| {
        result = result ++ field;
    }

    try std.testing.expectEqualStrings("abc", result);
}
```

```zig test
const std = @import("std");

test "inline for over heterogeneous tuple" {
    const tuple = .{ 42, true, "hello" };
    comptime var count: usize = 0;

    inline for (tuple) |_| {
        count += 1;
    }

    try std.testing.expectEqual(@as(usize, 3), count);
}
```

::callout{type="warning"}
A normal `for` cannot iterate a heterogeneous tuple usefully at runtime — the element types differ. `inline for` specializes each iteration at comptime, so each `field` can have a different type.
::

## Practical patterns

**Sum / reduce**

```zig test
const std = @import("std");

test "sum pattern" {
    const xs = [_]i32{ -1, 4, 2 };
    var total: i32 = 0;
    for (xs) |x| total += x;
    try std.testing.expectEqual(@as(i32, 5), total);
}
```

**Filter into a buffer** (manual, no hidden allocation)

```zig test
const std = @import("std");

test "filter pattern" {
    const xs = [_]u32{ 1, 2, 3, 4, 5, 6 };
    var evens: [6]u32 = undefined;
    var n: usize = 0;

    for (xs) |x| {
        if (x % 2 == 0) {
            evens[n] = x;
            n += 1;
        }
    }

    try std.testing.expectEqual(@as(usize, 3), n);
    try std.testing.expectEqual(@as(u32, 2), evens[0]);
    try std.testing.expectEqual(@as(u32, 6), evens[2]);
}
```

for (0..n) |i| { … }

const x = for (items) |v| {
    if (pred(v)) break v;
} else default;
